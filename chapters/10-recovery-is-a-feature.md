*Part III — Operating with Control*

# Chapter 10 — Recovery Is a Feature

Availability is not recoverability. A service can be running while the organization remains unable to recover it under realistic failure conditions. Recovery starts with a trusted state: the organization needs to know what state it is trying to restore and what dependencies are required to reach it. Recovery must be demonstrated: “we know how to recover RabbitMQ” is insufficient if the procedure exists only in one engineer’s memory. And recovery must survive people, which means documentation, redundancy and exercises.

> **Technical note — the shared components and how they fail.** A production OpenStack control plane typically relies on a small number of shared infrastructure services, each with its own recovery logic. The database is normally a MariaDB Galera cluster, usually written to through a single node behind the load balancer to avoid certification conflicts. It stays writable only while a majority of nodes (a quorum) can see each other; nodes that lose quorum move to a non-Primary state and refuse queries, and recovery after a full outage requires bootstrapping from the most advanced node, identified by the sequence number and the `safe_to_bootstrap` flag in `grastate.dat`; after an unclean stop every node reports an unknown sequence number and the most advanced one has to be found with `--wsrep-recover` before the flag is set. Bootstrapping the wrong node discards the transactions the others had committed, so this is the step to rehearse. The message bus is normally a RabbitMQ cluster. Queues are of a type: classic queues, mirrored or not, or quorum queues, which replicate to several nodes and stay available while a majority of their members is up, and which oslo.messaging recommends (`rabbit_quorum_queue`, with `rabbit_transient_quorum_queue` and `rabbit_stream_fanout` for the transient and fanout queues); RabbitMQ 4.0 removed classic queue mirroring altogether. A queue’s type is fixed at declaration, so moving to quorum queues is a migration in which the existing queues are deleted and recreated, in practice with the services that own them stopped; and a quorum queue needs a majority of its members, so a three-node cluster that loses two nodes loses its quorum queues, which is a reason to size the cluster for the failures it is expected to survive. On clusters that use RabbitMQ’s Mnesia metadata store, which includes every version before 3.13 and clusters upgraded in place since, the behaviour during a network partition is governed by `cluster_partition_handling`, and `pause_minority` is the usual choice for OpenStack; on clusters running the newer Khepri store, the default for new clusters in recent 4.x releases, that setting no longer applies, so the first thing to check is which store the cluster uses. Two more shared services are easy to forget in a recovery plan: memcached, which most deployments use for token validation and whose loss makes every API call slow or failing, and the load balancer with its virtual IP, which is what makes “stopping the APIs” a controlled action rather than a series of service shutdowns. Each of these components has documented failure and recovery procedures, and each is a candidate for the demonstrated recovery this chapter argues for. See the Galera documentation on quorum and crash recovery, the oslo.messaging RabbitMQ documentation, and the RabbitMQ documentation on quorum queues and partitions.

## Recovery is designed around capabilities

Recovery plans written only around components are misleading. Restarting Nova, restoring RabbitMQ or bringing a database online does not mean that the business capability of provisioning a VM has been restored; a component recovery test can pass while the service remains unavailable. Recovery should validate an end-to-end capability. For compute provisioning, that means demonstrating identity, API access, scheduling, image retrieval, networking, storage and workload creation, not the health of Nova processes. Dependencies are part of the plan: restoring Nova while its database, messaging or networking dependencies remain unhealthy restores nothing the business can use. And not every capability needs the same objective. Critical capabilities require stronger evidence; recovery has a business dimension as well as a technical one.

## The databases are the platform’s memory

The most consequential recovery on an OpenStack platform is the one Chapter 5’s dependency chain makes obvious and most recovery plans omit: restoring the control-plane databases. Every service keeps its own database, and the state of a single instance is spread across several of them: its record in Nova’s cell database and API database, its allocation in Placement, its ports in Neutron, its volumes in Cinder, its image in Glance. A backup strategy that restores one database to last night and another to this morning produces a platform in which the services disagree with each other and with the hypervisors: instances that Placement thinks exist and Nova does not, ports bound to nothing, volumes attached to instances that were deleted. Recovery of the databases therefore has to be designed as one operation with one point in time, and it has to be followed by reconciliation against reality. Backups that have never been restored into a test environment and compared with the running platform are a hope, not a capability.

## Unplanned host failure

Planned maintenance moves instances away before touching a host. A hardware failure gives no such warning, and the recovery it demands is different.

> **From the field.** A compute host failed, and its instances with it. The tools to move the instances elsewhere existed; the difficulty was elsewhere. Nothing on the platform could prove that the host was really dead rather than isolated, and there was no automatic fencing in place to make sure of it. Evacuating instances from a host that is still running them is how two copies of the same server end up writing to the same volume. The team therefore did not evacuate on the strength of the missing heartbeat. It reached the host’s out-of-band management interface, confirmed its state, shut the host down through it, and only then evacuated the instances to other hosts.

> **Technical note — evacuation and fencing.** `nova evacuate` rebuilds an instance on another host, reusing its volumes and, with shared instance storage, its disk; it is designed for a host that is down, and Nova requires the compute service on that host to be reported down before it will proceed. What Nova cannot know is whether the host is *actually* down or merely unreachable from the control plane. If the original host is still running the instance while its copy starts elsewhere, both write to the same storage. The safe sequence is therefore to fence the host, by powering it off through out-of-band management or by isolating it at the switch, before evacuating, and to treat the fencing step as the recovery’s precondition rather than a formality. The same reasoning applies to any automation that evacuates on a lost heartbeat: it must fence first or it will one day destroy the workload it was meant to save. See the Nova documentation on evacuating instances.

## The state that lies

An OpenStack platform accumulates records that no longer describe anything real, and every recovery, every host failure and every interrupted operation adds to them.

> **From the field.** On a long-lived platform, the databases had accumulated instances stuck in BUILD, in ERROR and in a deleting state that never completed, Neutron ports that belonged to nothing, and volumes marked as attached to instances that no longer existed. There was no single cause. The clean-up used the project tools where they existed and direct database corrections where they did not.

Such records are not harmless. They occupy quota, they distort capacity views, and they make every investigation start with the question of whether a given record describes reality. This residue deserves a place in normal operations rather than in emergencies. The projects provide tools for part of it: Placement allocations can be audited and healed with `nova-manage placement audit` and `nova-manage placement heal_allocations`; soft-deleted rows can be moved out of the live tables with `nova-manage db archive_deleted_rows` and purged; an instance’s state can be reset through the API. Direct database surgery remains necessary at times, and it should follow the discipline of any high-consequence change: a backup first, one record at a time, verification after. A platform whose state can be trusted is one whose operators can spend an incident investigating the problem instead of the records.

## Recovery must be exercised, with uncertainty and with different people

Real incidents rarely follow the runbook exactly. A useful exercise therefore introduces controlled uncertainty: a dependency is unavailable, an expected signal is missing, the primary expert is not present. The objective is to discover whether the organization can reason when the procedure does not match reality, not to make exercises artificially difficult. Exercises should also rotate participants. A recovery procedure that succeeds only when its author is present demonstrates the author’s competence rather than the organization’s resilience, and rotation exposes hidden assumptions while building a wider pool of capable operators.

Recovery exercises are also an architecture review. They expose dependencies that normal operation hides: if restoring one service requires manual intervention by another team, that dependency is now visible; if recovery requires an undocumented configuration, the documentation gap is now evidence. Every exercise should therefore end with the same question — what did this reveal that should now be different? — and the answer may be a documentation change, a monitoring improvement, an architecture change, a training need or a simplification. A failed recovery exercise is evidence that visibility, documentation, organization or architecture needs improvement.

## Recovery is a change under pressure

Recovery is itself a change, performed under greater uncertainty and greater pressure than a planned one. The normal change disciplines should be reused where possible: blast-radius control, monitoring, reversibility and stop conditions. Controlled degradation can be part of recovery, when the organization intentionally reduces functionality to protect the remaining service. Complexity becomes particularly expensive at this moment, which is why the question to ask of every dependency is how much of the platform must be understood or restored before the business capability operates again. Governance also enters here: someone must determine priorities, acceptable impact and authority during disruptive recovery (Chapter 13).

## Repair or rebuild

Engineers prefer repair because it preserves state. But unknown state has a cost, and there are situations in which rebuilding is safer than continued repair.

> **From the field.** A shared OpenStack test environment had been used by many teams for a long time. It had accumulated instances, ports, half-applied configuration changes and inconsistent assumptions from years of experimentation, to the point where nobody could say which part of its state was intentional. Each fix seemed to create the conditions for the next one, and debugging it meant debugging its history. The decision was to stop repairing it. The evidence that mattered was preserved, the intended baseline was written down, and the environment was rebuilt and validated progressively against that baseline.

The question to ask is whether the information contained in the current state is valuable enough to justify preserving its uncertainty. In a test environment, state mostly represents accumulated experimentation, and preserving an inconsistent one preserves uncertainty rather than value. Production changes the equation entirely. Production state represents business continuity: workloads, networks, volumes, identities and integrations cannot be discarded because the environment has become hard to understand, and the same technical mechanism that is appropriate for a test platform is unacceptable in production. Even there, however, repair becomes dangerous when each correction creates the conditions for the next, and the organization should ask whether continued repair is still reducing risk. The criterion is which option offers the highest probability of returning to a known, trusted state with acceptable business impact.

A rebuild is not safe merely because installation is automated. It needs a defined baseline, validation criteria and a way to prove the rebuilt environment is equivalent to the intended state; otherwise one unknown state has been replaced with another. But the capability to rebuild is itself evidence. An environment that can be reconstructed reliably from documented state proves that the organization knows its intended configuration, and non-production environments are the natural place to test that before it matters in production. And when repairing production, engineers should preserve evidence: the historical state may reveal the sequence that produced the failure, and once the platform is stable that evidence helps determine whether a deeper correction is needed. The objective is to recover without losing the ability to learn.

> **Principle.** Recovery is a feature because a platform is not operational if the organization cannot demonstrate how it returns to a trusted state.
